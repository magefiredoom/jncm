## 2. Directions chosen, and why

1. **Remove the level padding before any full run (new task T4.7).** Pack level k with level K+1-k: for L = 128, K = 12 every pair has exactly 129 positions (1+128, 13+116, ..., 59+70), so six sequences of 129 replace twelve of 128 and no slot is wasted. Attention stays inside each level through a two-block mask, so the function is the same; the test is equality with the padded path to float precision. *Estimate:* backbone FLOPs halve, a dev step drops from 4.46 s to about 2.3 to 2.6 s and a 10,000-step dev run from about 12.4 h to about 6.5 to 7 h. This helps every generator and JEPA run and every chunk of every chain, and it does not touch the method. It is a change under `jncm/generator/`, so it starts in plan mode. Other speed-ups (`torch.compile`, micro-batch 128, TF32) are smaller and wait until the packed step is measured.
2. **Run the g1 and g2 dev pilots now, in parallel with T4.7.** Each first contact with a code path on FIR has found a bug; the flow and regress heads, the JEPA joint trainer (trainable tokenizer, EMA, VICReg, collapse alarm) and their evals have never run on a GPU. These pilots are for correctness, not timing: their `sec_per_step` predates T4.7 and is not used for budgeting. Cost: 6 jobs, each `--wall=00:40:00`, about 4 requested H100-hours.
3. **Dev versus lite, by a rule fixed now.** After T4.7, one g0 dev re-pilot and one g0 lite pilot measure the packed step. If the packed dev step is at most 2.8 s, run the main comparison (G0, G1, G2 base) at dev size; otherwise run everything at lite size. Dev keeps the model size and the 1.31B generator positions the draft describes; lite is about ten times cheaper per step by FLOPs but sees 4 times fewer positions (batch 256), which weakens the sample-efficiency curves. The researcher can override the rule.
4. **The F16 corruption sweep comes next, at the chosen size**, before the G0/G1 full runs: three 2,000-step `ce` runs (`RUNBOOK.md` section 0.4). Its outcome fixes the corruption schedule for all arms.
5. **Full runs:** G0 and G1 together, then `scripts/gate_report.py`; G2 base next; then two or three JEPA ablations chosen by the remaining budget (the 2x2 over decoder-to-encoder gradient and VICReg first). The first chunk boundary of the first full run is the GPU check of resume (CUDA RNG state, data stream): compare the loss right after the resume with the record before it.
6. **Paper:** the method and setup sections are brought to final now (model sizes, scorer, accounting); results, figures and the title wait for the gates (`paper/draft.md`).

## 6. Risks

- **Queue time.** A dev run is several 3-hour chunks that each wait in the queue. Mitigations: T4.7, chains submitted as soon as a pilot passes, and lite as the fallback.
- **New bugs in untested paths** (flow, regress, JEPA, resume on GPU). Mitigation: step 1 before step 6, and the first chunk boundary checked by hand.
- **noisy + flow lags G0.** The open researcher option is a larger `d_k` or a smaller `sigma` (HANDOFF section 10); it would need a new tokenizer (2.3 H100-h) and the tokenizer trainer's resume fixes from T5.7/T5.8 first.
- **JEPA collapse or no gain.** The collapse alarm stops a run early; a negative G2 result is reported as such and changes the title, not the schedule.
- **The scorer.** It now runs GPT-2-large through `jncm/eval/gpt2_lean.py`. It matches Hugging Face to 1.3e-5 in logits and reproduces the T1.2 data row (Gen PPL 10.804267692 against 10.804267657, both entropies identical; `docs/STATE.md`). Any later change to the scorer must keep that comparison passing.
