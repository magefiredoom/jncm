## BLOCKER

### B1. Chunked runs throw away everything since the last `save_every`; at dev scale a chain can make no progress at all
- **Where:** `scripts/launch_phase.sh:239-259` (`compute_chunks`: `n = ceil(steps * sec_per_step / (0.9 * wall))`), `scripts/slurm/chain.sh:44` (`wall=03:00:00`), `configs/tinystories_dev.yaml:56` and `configs/jepa_dev.yaml:68` (`save_every: 5000`), `jncm/train_generator.py:572-597` (`latest.pt` is written only when `is_periodic`), and the same logic in `jncm/train_jepa.py`. No trainer handles SIGTERM/USR1. Milestone files (every 1,000 steps) carry no optimizer state, and resume ignores them.
- **What is wrong:** the chunk count assumes every chunk keeps about 90% of its wall clock as progress. In reality a chunk keeps only up to its last multiple of 5,000 steps. `RUNBOOK.md:294-298` already says "a job killed before step 5,000 restarts from scratch" for manual runs, but the kit's arithmetic ignores it.
- **Why it matters:** with a 3 h chunk and about 1-2 min of startup, chunk 1 reaches step 5,000 only if sec/step is below roughly 2.1. Above that, no chunk ever writes `latest.pt`, so every chunk restarts at step 0, burns its full 3 h, and the run never writes `DONE`. Example: 2.5 s/step gives 3 chunks = 9 H100-hours and no finished run. Below the cliff it still wastes time: at 1.5 s/step chunk 1 reaches step 7,200 and keeps 5,000, losing about 55 min per run.
- **How likely:** dev generator step ≈ 6 × 85M params × 1.57M padded tokens ≈ 8e14 FLOP, i.e. about 2 s/step at 400 TFLOP/s. JEPA dev also runs the tokenizer forward and backward plus the EMA encoder, so it is heavier. UNVERIFIED: the dev pilots' `sec_per_step` (jobs 3566052/3566054/3566055/3566058) decide it. Lite (batch 256) is about 4x cheaper and should stay below the cliff.
- **Fix:** write `latest.pt` (with optimizer state) at every milestone, i.e. every 1,000 steps. Also make `compute_chunks` stop with an error when `save_every_effective * sec_per_step > 0.8 * wall`. Optionally add `--signal=B:USR1@300` with a handler that saves `latest.pt`.
- **Test that would have caught it:** in `tests/test_launch_phase.py`, write a fake pilot `metrics.jsonl` with `sec_per_step 2.5` and run `g0 full` with the dev config. Expect an error, or an export that lowers `save_every`; today it prints 3 chunks. In the trainer tests, run smoke with `max_steps=10`, `milestones` at step 5 and `save_every=100`, stop after step 7, resume, and assert `start_step >= 5`.

### B2. JEPA runs start from the fully trained staged tokenizer but are charged no tokenizer positions
- **Where:** `jncm/train_jepa.py:111-124` (`load_online_tokenizer`; the docstring says the tokenizer budget is "kept as bookkeeping; SPEC 6.2 does not charge it"), `jncm/train_jepa.py:175` (`total_positions = joint_positions`), and `tok_offset` stored but never added. The launch kit makes this the only G2 path: `scripts/launch_phase.sh:482` (`require_checkpoint results/tok_noisy_10k/...`), `:507` (`TOKENIZER=results/${TOK_RUN}/ckpt/latest.pt`), and `scripts/slurm/jepa.sbatch:63` (`TOKENIZER` required). The trainer logic predates the range (T5.3, `56ed093`); the range wires it into every G2 run.
- **What is wrong:** SPEC 6.2 counts a joint run once because "each sample is seen once by both objectives". That holds only if E and D start untrained. Here they start from `tok_noisy_10k`, which has already seen 655M positions. Neither SPEC 8 nor QUESTIONS.md nor any ASSUMPTION records this warm start; STATE.md:192 and :575 describe it only as bookkeeping.
- **Why it matters:** the headline G2 comparison (paper §1, contribution 4; §4.1) plots against `total_positions`. Staged curves start at +655M, JEPA curves at 0 with the same trained tokenizer inside. At 10k dev steps: JEPA 1.31B (conservative 2.62B) against staged 1.97B. A sample-efficiency "win" of up to 655M positions would be pure accounting. Lite: 0.33B against 0.98B.
- **Fix (researcher decision; SPEC 8 does not say):** either (a) train JEPA from scratch, which needs a path that builds a fresh tokenizer when `TOKENIZER` is unset, or (b) keep the warm start and charge it: `total_positions = tok_offset + joint_positions`, `total_positions_conservative = tok_offset + 2 * joint_positions`. Record the choice in QUESTIONS.md and the paper's setup.
- **Test that would have caught it:** in `tests/test_train_jepa.py`, warm-start from a tokenizer checkpoint with `tok_positions = T`. Assert the first record's `total_positions == T + B*L` for option (b), or that the trainer refuses a warm start without an explicit flag for option (a).

## MAJOR

### M1. Every G1 eval job (flow, regress) fails at startup
- **Where:** `scripts/slurm/eval.sbatch:95-104` builds `run_eval.py` with `--config ${CONFIG:-configs/tinystories_dev.yaml}` and has no `HEAD`/quantizer override. `configs/tinystories_dev.yaml:10,30` (and the lite config) set `quantizer: vq` and `head: ce`. `scripts/run_eval.py:129-141` raises on a mismatch. `scripts/launch_phase.sh:374-389` (`launch_eval`) passes no `HEAD`.
- **Reproduced on CPU this session:** `resolve_checkpoint_config(load_config("configs/tinystories_dev.yaml"), {"config": <dev cfg with head=flow, quantizer=noisy>}, ...)` raises `ValueError: checkpoint milestone_010.pt head='flow' does not match config head 'ce'`.
- **Why it matters:** the queued pilot evals 3566056/3566057 (dev) and 3566095/3566096 (lite) will fail, and so would the full G1 evals after the training GPU time is spent. Without them there is no Gen PPL or diversity for flow and regress, so G1 cannot be judged. Each failure is cheap, but the gate is blocked. G0 (ce) and G2 (joint checkpoints use their own config) are not affected.
- **Fix:** give `eval.sbatch` an optional `HEAD` using the same mapping as `gen.sbatch` (`--set generator.head=$HEAD --set tokenizer.quantizer=$quant`), and have `launch_eval` pass it. Alternatively, have `run_eval.py` take head and quantizer from the staged checkpoint and check them against the tokenizer checkpoint instead of the CLI YAML.
- **Test that would have caught it:** in `tests/test_run_eval.py`, the CLI dev config plus a flow checkpoint must resolve or evaluate; today it raises. In `tests/test_eval_sbatch.py`, `HEAD=flow` must produce both `--set` flags. In `tests/test_launch_phase.py`, every g1 eval export must contain `HEAD=`.

### M2. Resume replays the data stream and all random draws from step 0
- **Where:** `jncm/train_generator.py:470-476` (resume restores model and optimizer only; `rng` is re-seeded from `cfg.seed`; the loader is a fresh `InfiniteBatchIterator`), `jncm/data.py:40-60` (seeded `RandomState` permutation), and `jncm/train_jepa.py:271-281` likewise. This is the known Q5 limitation ("acceptable for dev"), but T4.5 makes chunked resume the normal path for every full run.
- **What is wrong:** after a resume at step 5,000, steps 5,000-9,999 see exactly batches 0-4,999 again, with the same corruption and channel-noise draws, instead of continuing the epoch.
- **Why it matters:** (a) a chunked run's second half sees no data its first half did not, unlike an unchunked run; (b) arms with different chunk splits see different data. Splits differ because the ce head (+38M params), flow (`n_rep=4`) and regress run at different speeds, and dev and lite differ too, which confounds the comparison. (c) A chunked run cannot be reproduced against an uninterrupted one. The effect on final metrics is UNVERIFIED; TinyStories is already seen about 2.6 times in 10k dev steps.
- **Fix:** store the iterator state (epoch `RandomState.get_state()` plus cursor) and `rng.get_state()` (and the torch/CUDA RNG) in `latest.pt` and restore them. A cheaper alternative is to advance the iterator by `start_step` batches on resume.
- **Test that would have caught it:** on CPU with the smoke config, train 10 steps straight, and separately 5 steps plus a resume to 10. Assert identical per-step batch hashes and identical final parameters.

## MINOR

### m1. Pilot `sec_per_step` overstates steady-state cost
`jncm/train_generator.py:537` (and `train_jepa.py:365`, `train_tokenizer.py`) time everything since loop start. In a 300-step pilot that includes step-0 and final diagnostics with `GEN_PPL=1` (sampling plus GPT-2-large scoring), ten milestone saves (one every 30 steps) and CUDA warm-up. Full runs have no `GEN_PPL` and save milestones every 1,000 steps. The over-estimate only adds cheap no-op chunks, but inflated `budget.py` totals can push the dev-versus-lite decision toward lite. Size: UNVERIFIED; compare the pilot's `sec_per_step` with `sacct` Elapsed/300. Fix: time only the training step, or steps 50..N, and log it as `train_sec_per_step` beside the current field. Test: inject a slow fake scorer and assert the new field excludes the delay.

### m2. JEPA draws one nested-dropout cut per micro-batch, not per batch
`jncm/jepa/joint.py:293` calls `sample_cutoff` inside `joint_loss`, which runs `grad_accum` times per step (`jncm/train_jepa.py:319`). SPEC 4.4 says one cut per batch. The decoder therefore sees 16 cuts per step in dev, 4 in lite, and 1 per 512-batch in the staged tokenizer, and the logged `cut` is only the last micro-batch's. Fix: sample once per optimizer step in `train_jepa` and pass it in, or record an ASSUMPTION. Test: with `grad_accum=4`, count `sample_cutoff` calls (expect 1) and check that all micro-batches use the same cut.

### m3. F17 is only half applied: the conditioning chain still runs under bf16
`frozen_codes` (`jncm/train_generator.py:174`) disables autocast for encode and corruption. However, `embed_levels`, called at `:228` inside the outer autocast, runs `pooled_reconstructions` (`jncm/generator/backbone.py:335`, called at `:378`). That function applies `tokenizer.contrib` (Linear, interpolate, depthwise conv) in bf16, so each contribution to the conditioning carries bf16 rounding in training but not in fp32 sampling. The effect is likely small, since the result feeds a bf16 Linear anyway (UNVERIFIED); the targets are fp32 as intended. Fix: build the pooled reconstructions inside the autocast-disabled block of the frozen path. Test: on CPU under `torch.autocast("cpu", dtype=torch.bfloat16)`, assert the pooled reconstructions are float32 and equal the fp32 reference.

### m4. `g2 full --ablations` stops after a partial submission
`scripts/launch_phase.sh:506` sizes each ablation from its own pilot (`pilot_jepa_no_vicreg`, ...), which a default pilot run never creates. The base chain and its eval are submitted, then the script exits at the first ablation with "no sec_per_step". Fix: fall back to the `pilot_jepa_base` measurement (same model, only flags differ), or compute every chunk count before the first `sbatch`. Test: `g2 full --ablations` with only base pilot metrics must either plan all 7 chains or make no fake-`sbatch` call.

### m5. `budget.py` can no longer produce a clean total
`scripts/budget.py:38-49`: since T5.6 the pilots reuse the finished tokenizers, so `pilot_tok_vq` and `pilot_tok_noisy` never exist. The six JEPA ablations have no pilots either. Their rows are always `MISSING`, so the tool always reports its total as untrustworthy. Fix: show runs with `DONE` as 0 h and size the ablations from `pilot_jepa_base`. Test: with `results/tok_vq_10k/DONE` and only base pilots, there are no `MISSING` rows and the total covers every generator and JEPA run.

### m6. Shell variables leak into jobs through `--export=ALL`
`scripts/launch_phase.sh` never clears `SETS` (only around the G2 loop, `:502`), `GEN_PPL`, `N_SAMPLES` or `N_SEEDS` (these are set only in pilot mode). If `SETS` is still exported from the F16 sweep (STATE "Next 3 steps", item 3), it silently applies a corruption override to G0/G1 full runs. An exported `N_SAMPLES=32` shrinks the full eval below SPEC 6.1's 256 × 5. Fix: `unset SETS GEN_PPL N_SAMPLES N_SEEDS` at the top of the script, then set each variable explicitly. Test: a fake `sbatch` that dumps its environment; run `g1 full` with these variables exported and assert they are absent.

### m7. The collapse alarm cannot fire in a 10k-step run (pre-existing, T5.3, outside the range)
`CollapseAlarm.update` (`jncm/jepa/diagnostics.py:153`) counts calls, and those happen only at diagnostics (`jncm/train_jepa.py:156`, every 500 steps). "200 consecutive steps" therefore means 100,000 steps. The alarm only logs, so no GPU time is at stake, but a collapsing `jepa_no_vicreg` would go unflagged. Fix: express patience in eval units, `ceil(200 / eval_every)`, or update every step. Test: with `eval_every=500`, two evals below threshold set the flag.
