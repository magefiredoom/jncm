## MAJOR

### M1. Figure A is a placeholder in every state once Table 1 is final
- **Where:** `scripts/plot_fig_a.py:66-68` (every record checked by `eval_reason(rec, CURVE_SAMPLES)`), with `CURVE_SAMPLES = 256` at `scripts/paper_results.py:47`.
- **What:** the 1024 x 5 final eval writes the same `step_<n>.seed_<i>.json` shards as the 256-sample final milestone, and its merge rewrites `eval/step_<n>.json` (`scripts/run_eval.py:477`, `merge_shards`; STATE "FIR jobs", T4.9 block). The 256-sample final record is therefore replaced, never kept beside it. `arm_series` then daggers the arm (`eval 1024 x 5 (needs 256 x 5)`), draws it dashed and adds the PLACEHOLDER banner.
  - With the final eval at 256 x 5, Table 1 daggers the row instead. No state of the results directory makes both final (fixture above).
- **Why it matters:** E7's acceptance and P1 need a final Figure A from the same records as Table 1. As written, the paper's main figure cannot lose its banner without a code change on the day the results land.
- **Fix:** for curves, accept any record with `n_seeds == 5` and `n_samples >= 256`, and mark the last point if it is 1024 x 5 (a marker, and a caption line such as "final point: 1024 samples").
  - Alternatively, keep the 256-sample final under its own name. That would be a `run_eval.py` change, which falls under the pull rule while E4/E5 run.
- **Test that would have caught it:** a fixture with nine 256 x 5 milestones, a 1024 x 5 final at fraction 1.0, and `DONE`. Assert `table_rows` reasons `== []` and `arm_series` reasons `== []` on the same directory. The PR's tests use 256 everywhere for Figure A and 1024 everywhere for Table 1, so neither covers the real end state.

### M2. The Params column under-reports the JEPA arm, which trains its tokenizer
- **Where:** `scripts/paper_results.py:105-111` (`model_params` = backbone + head) and the caption at `:184-186` ("the frozen tokenizer is excluded").
- **What:** in a joint run the tokenizer is not frozen. `jncm/train_jepa.py:152-153` sets `requires_grad_(True)` on it, and `:268-273` gives AdamW `joint_named_parameters(tokenizer, backbone, head)`.
  - On the real `pilot_jepa_base` record the column prints 100.5M (85,459,200 + 15,065,184), while the run trains 108.8M (plus the 8,270,048-parameter tokenizer). That is the same column value as noisy + flow, whose tokenizer is frozen.
  - The EMA copy gets no gradient and is rightly not counted.
- **Why it matters:** this is the column P1a's fairness argument rests on ("the backbone is shared and identical"; TASKS P1a). For the JEPA arm, a reader would believe the parameter budgets are equal when JEPA updates 8.3% more parameters. SPEC 5.7 asks for parameter counts per arm.
- **Fix:** report trained parameters. For a staged arm that is backbone + head; for a joint arm (a record with `total_positions_conservative`) it is tokenizer + backbone + head. Alternatively, keep backbone + head and add a joint-run footnote with `n_params_tokenizer`. Either way, the caption must stop saying the tokenizer is frozen for every arm.
- **Test that would have caught it:** a joint fixture record (`total_positions_conservative` set, `n_params_tokenizer` 8,270,048). Assert that its Params cell is 108.8M, or that the footnote with the tokenizer count is present, and that the caption does not call a joint run's tokenizer frozen.

### M3. Figure B cannot show the draft's claim, and its one R2 curve is not comparable to later staged ones
- **Where:** `scripts/plot_fig_b.py:12-17` and `:46-50` (`R2_ARMS`), and `paper/draft.md` 4.3 ("including the collapse of the regression head at the coarsest level").
- **What:**
  - Only `train_jepa.py` logs `r2` (`jncm/jepa/diagnostics.py:128`), on its training batch, against its own targets t_k (EMA or online, depending on the arm).
  - The staged flow and regress generators log no per-level R2, and no eval computes one. The right panel can therefore only show JEPA, with the staged arms listed as "not logged".
  - The claim the draft names (C3, regress collapsing at level 1) has no data source.
- **Why it matters:** as written, E7's Figure B is not deliverable from any record that exists or will exist after E4/E5. If a staged R2 is added later on a held-out batch against the frozen c_k, it is not comparable with JEPA's training-batch R2 against moving targets. That would make the panel unfair across arms (review item 8).
- **Fix:** a new task, an eval-time per-level R2: predictions c-hat_k against the frozen tokenizer's c_k (and JEPA against its t_k), on the same held-out batch, written into the eval records.
  - The likely home is `scripts/run_eval.py`, which falls under the pull rule until the E4/E5 chains finish.
  - Figure B then reads only eval records, as TASKS E7 already says ("from the eval and diagnostic records").
  - Runtime cost: UNVERIFIED. A pilot eval with the new metric would confirm it.
- **Test that would have caught it:** a fixture where the flow and regress arms carry an eval-time `r2` and the JEPA arm carries only the training-batch one. Assert that the figure refuses to put the two sources on one axis, or labels them apart.

## MINOR

### m1. A run without DONE is never final, against SPEC 10.2 (v1.7)
- **Where:** `scripts/paper_results.py:79-80`, `scripts/plot_fig_b.py:94-95`.
- **What:** SPEC 10.2 (v1.7) says a run counts as trained once its final milestone exists at the expected size; `DONE` is needed only for chaining, resume bookkeeping and pilots. A main run whose final resume save failed after its final milestone (SPEC 10.3, the 2026-11-21 quota case) stays daggered for good.
- **Fix:** when the last eval record has fraction 1.0, report a missing `DONE` as a note ("final resume save missing, SPEC 10.2"), not as a placeholder reason. For Figure B, which reads `metrics.jsonl`, check for the final milestone file.
- **Test:** a fixture with a 1024 x 5 final at fraction 1.0 and no `DONE`; expect no dagger and the note.

### m2. Unmerged or malformed eval records are shown as a missing run
- **Where:** `scripts/paper_results.py:97-102` (`load_arm` catches `FileNotFoundError` and `ValueError` and returns `None`).
- **What:** `gate_report.load_run` raises `ValueError` both when only per-seed shards exist (`--merge` not run yet) and when an aggregate has no `ppl_mean` (a damaged file). Both become "no merged eval records" in Table 1 and "MISSING, not drawn" in Figure A.
- **Why it matters:** the first case hides a one-command fix, since T4.9's merge job may not have run. The second hides a damaged result file, a silent fallback that AGENTS and CLAUDE.md forbid.
- **Fix:** keep the exception message as the row's reason, and re-raise for a malformed aggregate.
- **Test:** an eval directory holding only `step_*.seed_*.json`, where the reason must name `--merge`; and an aggregate without `ppl_mean`, where the scripts must raise.
